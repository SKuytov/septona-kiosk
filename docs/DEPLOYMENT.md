# Разгръщане на сървъра

Управляващата платформа е един Docker стек: Node.js сървър + PostgreSQL. Тя обслужва
администрацията, синхронизацията към панелите и уеб версията на киоска.

За индустриална среда препоръчаният вариант е **виртуална машина с Ubuntu Server LTS
върху Proxmox**. Причините са в [Къде да работи платформата](#къде-да-работи-платформата).

---

## Бърза инсталация

На нов Ubuntu Server 22.04 или 24.04:

```bash
curl -fsSL https://raw.githubusercontent.com/SKuytov/septona-kiosk/main/deploy/install.sh | sudo bash
```

Скриптът инсталира Docker, изтегля проекта в `/opt/septona-kiosk`, генерира случайни
пароли и стартира всичко. Отнема 3–6 минути на чиста машина.

Накрая извежда адресите и **паролата на администратора — запишете я веднага**:

```
  Management platform   http://10.0.0.20:8080/
  Kiosk in a browser    http://10.0.0.20:8080/kiosk/

  Sign in with
      email     admin@septona.local
      password  HqqxwKKGhEAknrWi
```

Настройки чрез променливи на средата:

```bash
curl -fsSL .../install.sh -o install.sh
sudo HTTP_PORT=9090 INSTALL_DIR=/srv/septona bash install.sh
```

| Променлива    | По подразбиране        | Значение                         |
| ------------- | ---------------------- | -------------------------------- |
| `HTTP_PORT`   | `8080`                 | Външният порт на платформата     |
| `INSTALL_DIR` | `/opt/septona-kiosk`   | Къде се разполага проектът       |
| `BRANCH`      | `main`                 | Клон от хранилището              |

Скриптът е безопасен за повторно изпълнение — съществуващ `.env` никога не се
презаписва, така че повторното пускане е **обновяване** без смяна на паролите.

## Къде да работи платформата

### Proxmox + Ubuntu Server LTS — препоръчано

Това е правилният избор за производствена среда:

- **Снимки (snapshots).** Правите снимка преди обновяване; при проблем се връщате за
  секунди. Това е най-силният аргумент — при споделен хостинг такова нещо няма.
- **Резервни копия.** Proxmox Backup Server прави копие на цялата машина, включително
  документите и базата, по график.
- **Работи без интернет.** Панелите се синхронизират по локалната мрежа. Ако връзката
  на завода падне, всичко продължава да работи.
- **Данните остават при вас.** Вътрешни документи — политики, планове за евакуация —
  не напускат вашата мрежа.
- **Ниска латентност.** Изтеглянето на 55 PDF файла по локална мрежа е въпрос на
  секунди.

Достатъчни ресурси за този товар:

| Ресурс | Минимум | Препоръчано |
| ------ | ------- | ----------- |
| vCPU   | 2       | 2–4         |
| RAM    | 2 GB    | 4 GB        |
| Диск   | 20 GB   | 40 GB (SSD/NVMe) |

Дискът се пълни основно от версиите на документите. Всяка ревизия се пази завинаги
заради одитната следа, така че 40 GB дават много години запас при този обем.

### Споделен хостинг (SuperHosting) — не се препоръчва

Работи технически, но има реални ограничения: обикновено няма Docker и root достъп,
няма снимки, а вътрешните документи се озовават при трета страна. Смислен е само ако
панели извън локалната мрежа трябва да се синхронизират през интернет — а това се
решава по-добре с VPN към Proxmox машината.

## Създаване на виртуалната машина в Proxmox

1. Изтеглете **Ubuntu Server 24.04 LTS** ISO в Proxmox:
   `Datacenter > <възел> > local (ISO Images) > Download from URL`
   ```
   https://releases.ubuntu.com/24.04/ubuntu-24.04-live-server-amd64.iso
   ```

2. `Create VM` със следните настройки:

   | Раздел  | Настройка                                                        |
   | ------- | ---------------------------------------------------------------- |
   | General | Name: `septona-kiosk` · Start at boot: **да**                    |
   | OS      | ISO-то отгоре · Type: Linux · Version: 6.x                       |
   | System  | Machine `q35` · BIOS `OVMF (UEFI)` · Qemu Agent: **да**          |
   | Disks   | 40 GB · Bus `VirtIO Block` · Discard: **да** · SSD emulation: **да** |
   | CPU     | 2–4 ядра · Type **`host`**                                       |
   | Memory  | 4096 MB · Ballooning: изключено                                  |
   | Network | Bridge `vmbr0` · Model **`VirtIO`**                              |

   `Type: host` при процесора и `VirtIO` за диск и мрежа дават осезаемо по-добра
   производителност от съвместимите стойности по подразбиране.

3. Инсталирайте Ubuntu. По време на инсталацията:
   - Изберете **статичен IP адрес** (например `10.0.0.20/24`). Панелите се насочват
     към този адрес, така че той не бива да се променя.
   - Отметнете **Install OpenSSH server**.
   - Не са нужни никакви допълнителни snap пакети.

4. След първото стартиране:

   ```bash
   sudo apt update && sudo apt upgrade -y
   sudo apt install -y qemu-guest-agent && sudo systemctl enable --now qemu-guest-agent
   ```

5. Пуснете инсталатора от [Бърза инсталация](#бърза-инсталация).

6. Направете снимка в Proxmox: `<VM> > Snapshots > Take Snapshot`, име `clean-install`.

## След инсталацията

1. **Сменете паролата на администратора** — влезте и отидете в `Потребители`.
2. **Създайте устройство** за всеки панел: `Устройства > Ново устройство`. Копирайте
   ключа — показва се веднъж.
3. **Настройте панела**: задръжте логото 3 секунди, PIN `2470`, въведете адреса на
   сървъра (`http://10.0.0.20:8080`) и ключа на устройството.
4. **Заредете началните документи**, ако още не са. Копирайте архива на сървъра
   (от вашия компютър: `scp KIOSK_DOCS.zip kuytov@10.0.0.20:~/`) и изпълнете:
   ```bash
   sudo bash /opt/septona-kiosk/deploy/import-docs.sh ~/KIOSK_DOCS.zip
   ```
   Папките от първо ниво стават категории. Папките `*_BG` / `*_ENG` вътре в тях не
   стават подкатегории — документите в тях се маркират с този език. Скриптът може да
   се изпълни повторно без да създава дубликати. Вместо това можете да качвате
   документи и през платформата за управление.

### Защитна стена

Ако е включена `ufw`, отворете порта на платформата само към локалната мрежа:

```bash
sudo ufw allow from 10.0.0.0/24 to any port 8080 proto tcp
sudo ufw allow OpenSSH
sudo ufw enable
```

## Обслужване

```bash
cd /opt/septona-kiosk

docker compose logs -f            # дневници на живо
docker compose ps                 # състояние
docker compose restart server     # рестарт само на приложението
docker compose down               # спиране
sudo bash deploy/install.sh       # обновяване до последната версия
```

### Резервни копия

Документите са в Docker том `files`, базата — в `db-data`. Пълно копие:

```bash
cd /opt/septona-kiosk
docker compose exec -T db pg_dump -U septona septona_kiosk | gzip > db-$(date +%F).sql.gz
docker run --rm -v septona-kiosk_files:/data -v "$PWD:/out" alpine \
  tar czf /out/files-$(date +%F).tar.gz -C /data .
```

Ежедневно копие в 02:00 през `cron`:

```bash
sudo crontab -e
# 0 2 * * * cd /opt/septona-kiosk && docker compose exec -T db pg_dump -U septona septona_kiosk | gzip > /var/backups/septona-db-$(date +\%F).sql.gz
```

При Proxmox снимката на цялата машина покрива и двете и е по-простият вариант.

### Възстановяване

```bash
cd /opt/septona-kiosk
gunzip -c db-2026-08-07.sql.gz | docker compose exec -T db psql -U septona septona_kiosk
docker run --rm -v septona-kiosk_files:/data -v "$PWD:/in" alpine \
  tar xzf /in/files-2026-08-07.tar.gz -C /data
docker compose restart server
```

## Достъп от всеки компютър

По подразбиране платформата се вижда само в локалната мрежа. Тази глава я публикува на
ваш адрес с истински сертификат — например `https://docs.partpulse-app.com` — без да се
отваря нито един входящ порт.

### Защо през тунел, а не с пренасочване на порт

Сървърът сам набира изходяща връзка към Cloudflare и трафикът се връща по нея. От това
следват три неща, всяко от които има значение:

- **Няма отворен входящ порт.** Не се пипа рутерът, не се иска правило от ИТ отдела,
  няма изложен порт 443, който да бъде сканиран.
- **Сертификатът е издаден на вашия домейн** от Cloudflare и е валиден за всеки браузър.
  Няма предупреждения за самоподписан сертификат.
- **FortiGate няма основание да блокира адреса.** Това е практическата разлика спрямо
  безплатните адреси на VPN услугите: FortiGuard класифицира Tailscale в категория
  „Proxy“, а много фирмени политики блокират цялата категория по подразбиране — самата
  документация на Tailscale посочва, че при дълбока инспекция на FortiGate връзката
  просто не се получава и заобиколно решение няма. Адрес на собствен домейн не попада в
  тази категория.

### Какво е нужно

- Домейн, чиито nameserver-и могат да сочат към Cloudflare. Cloudflare е безплатен;
  домейнът е около 10–20 лв. годишно, ако още нямате.
- Пет минути при регистратора (Hostinger, SuperHosting) за смяна на nameserver-ите.

> **Внимание за поддомейн на съществуващ домейн.** Cloudflare може да обслужва отделен
> поддомейн, без да поема целия домейн, само в платен план Business. В безплатния план
> nameserver-ите на **целия** домейн минават към Cloudflare. Cloudflare пренася
> съществуващите записи автоматично, но ако на този домейн има работещ сайт или поща,
> проверете записите (MX, TXT, SPF/DKIM) веднага след прехвърлянето. Ако не искате да
> местите домейн с поща, използвайте другия си домейн.

### Стъпка 1 — Домейнът в Cloudflare

1. Регистрирайте се в <https://dash.cloudflare.com> и добавете домейна (план Free).
2. Cloudflare показва два nameserver-а. Въведете ги при регистратора на мястото на
   текущите.
3. Изчакайте домейнът да стане **Active** (обикновено до час).

### Стъпка 2 — Тунелът в Cloudflare

1. Zero Trust → **Networks → Tunnels → Create a tunnel → Cloudflared**.
2. Име: `septona-kiosk`. Запишете.
3. На екрана с инсталационните команди копирайте **само токена** — дългата стойност
   след `--token`, започва с `eyJ`. Него ще подадете на скрипта.
4. Раздел **Public Hostname → Add a public hostname**:

   | Поле | Стойност |
   | ---- | -------- |
   | Subdomain | `docs` |
   | Domain | вашият домейн |
   | Path | празно |
   | Type | `HTTP` |
   | URL | `server:8080` |

   `server:8080` е име на услугата в Docker, не адрес в мрежата — конекторът работи в
   същата Docker мрежа. Не пишете `localhost`.

### Стъпка 3 — Сървърът

```bash
sudo bash /opt/septona-kiosk/deploy/setup-tunnel.sh
```

Скриптът иска токена и адреса, записва ги в `.env`, вдига конектора и проверява, че
адресът наистина отговаря отвън. Безопасен е за повторно изпълнение.

Преди да промени каквото и да е, скриптът проверява дали администраторът още използва
фабричната парола `septona-admin`. Ако да — спира и не пипа нищо. Публично известна
парола на публичен адрес е отворена врата, затова:

```
Спирам: администраторът още използва фабричната парола.
```

Сменете я от локалната мрежа (горе вдясно → Смяна на парола) и стартирайте отново.

### Какво се променя при публикуване

Задаването на `PUBLIC_ORIGIN` в `.env` превключва сървъра в режим „изложен в интернет“:

| Мярка | Действие |
| ----- | -------- |
| Отказ при слаба тайна | Сървърът не стартира при `JWT_SECRET` под 24 знака или познат такъв. С познат ключ външен човек може да си издаде администраторски токен, без да знае парола. |
| Отказ при фабрична парола | Сървърът не стартира, докато администратор използва `septona-admin`. |
| HSTS | Браузърът отказва да се свърже по обикновен HTTP към този адрес за една година. Заглавката се изпраща само по HTTPS, за да не се засегне локалният адрес. |
| Ограничение на опитите за вход | 8 неуспешни опита за акаунт и 10 за IP адрес на 15 минути. Броят се само неуспешните, така че нормалната работа не заключва никого. |
| CSP и заглавки | Заключен произход на скриптовете, забрана за вграждане в чужд сайт, `Referrer-Policy: no-referrer`, за да не изтича адресът за преглед на документ. |
| Затворен CORS | API-то приема заявки само от собствения си адрес и от Android приложението. |

Панелите в цеха не се променят — те продължават по локалния адрес.

### Проверка

```bash
curl -I https://docs.вашият-домейн/api/health     # 200 и Strict-Transport-Security
cd /opt/septona-kiosk && docker compose logs -f cloudflared
```

Сертификатът:

```bash
echo | openssl s_client -connect docs.вашият-домейн:443 \
  -servername docs.вашият-домейн 2>/dev/null | openssl x509 -noout -issuer -dates
```

### Спиране на публичния достъп

```bash
cd /opt/septona-kiosk
docker compose stop cloudflared        # временно
```

За окончателно спиране изтрийте `TUNNEL_TOKEN` и `PUBLIC_ORIGIN` от `.env`, после
`docker compose up -d`, и премахнете тунела в Cloudflare.

### Ако искате и втора ключалка

Cloudflare Access поставя проверка **пред** платформата — външен човек не вижда дори
екрана за вход. Безплатно до 50 потребители, с еднократен код по имейл. Zero Trust →
Access → Applications → Add an application → Self-hosted, за `docs.вашият-домейн`, и
политика Allow с конкретните имейли. Не е задължително: платформата има собствен вход.

### Другите варианти, и защо не са първи избор

| Вариант | Защо не |
| ------- | ------- |
| **Tailscale Funnel** | Не изисква домейн и издава валиден сертификат, но адресът е `*.ts.net`. FortiGuard класифицира Tailscale в „Proxy“ и фирмени политики често блокират категорията. Ограничен е и до портове 443/8443/10000. |
| **Cloudflare Quick Tunnel** (`trycloudflare.com`) | Без акаунт и без домейн, но адресът е случаен и се сменя при всеки рестарт, с таван 200 едновременни заявки. Cloudflare изрично не го препоръчва за постоянна работа. Подходящ само за еднократна демонстрация. |
| **Пренасочване на порт + Caddy** | Работи, но изисква публичен IP адрес, отворен порт 443 към сървъра и правило в защитната стена — точно това, което тунелът избягва. |

Ако все пак предпочитате Caddy пред собствен порт:

```
docs.вашият-домейн {
    reverse_proxy 127.0.0.1:8080
}
```

Caddy сам издава и подновява сертификата, при условие че портове 80 и 443 достигат
машината отвън.

### Какво означава HTTPS за браузърната версия

Service Worker се регистрира само в „сигурен контекст“ — HTTPS или `localhost`. По
обикновен HTTP към адрес в мрежата (`http://10.0.0.20:8080/kiosk/`) той няма да се
включи; през публичния адрес се включва.

На практика това има малко значение за уеб версията: самата страница се доставя от
сървъра, така че ако сървърът е недостъпен, страницата така или иначе не се зарежда.
Документите и списъците се пазят в IndexedDB, който работи и по обикновен HTTP —
веднъж отворена, страницата продължава да показва всичко без мрежа. Service Worker
добавя само устойчивост при презареждане по време на кратко прекъсване.

**Истинската офлайн работа е задача на Android приложението**, което носи целия
интерфейс в APK-то и няма това ограничение. Панелите трябва да ползват приложението;
браузърната версия е за компютри и телефони в мрежата.

## Отстраняване на проблеми

| Симптом | Проверка |
| ------- | -------- |
| „Възникна проблем при анализирането на пакета" при инсталиране на APK | Изтеглете файла отново — често се получава при непълно копиране. Проверете подписа с `apksigner verify <файл>.apk`. Изисква се Android 5.1 или по-нов. |
| Инсталаторът спира с „Port 8080 is already in use" | Друга услуга заема порта. `sudo ss -ltnp \| grep 8080`, после `HTTP_PORT=9090 sudo -E bash install.sh` |
| Платформата не отговаря | `docker compose ps` и `docker compose logs server` |
| „Няма връзка със сървъра" на панела | Проверете адреса в сервизния екран; от панела трябва да се отваря `http://<ip>:8080/api/health` |
| Панелът не се обновява | `Устройства` показва последна връзка; синхронизацията е на всеки 15 мин |
| Базата не тръгва | `docker compose logs db`; при повреден том се възстановява от копие |
| Публичният адрес не отговаря | `docker compose logs cloudflared`. Проверете, че Public Hostname сочи `HTTP` → `server:8080`, а домейнът е Active в Cloudflare. |
| Сървърът отказва да стартира след `setup-tunnel.sh` | Прочетете съобщението: слаб `JWT_SECRET` или фабрична администраторска парола. И двете се оправят от локалната мрежа. |
| „Твърде много неуспешни опити" при вход | Ограничението е 8 опита на акаунт за 15 минути. Изчакайте или рестартирайте `server`. |
